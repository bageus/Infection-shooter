# Infection-shooter — план оптимизации FPS и загрузки

Дата: 11.10.2026. Версия плана: 1.0.
Репозиторий: https://github.com/bageus/Infection-shooter
Основа аудита: main, коммит `eb0161ea53e0004ca3294dadbac96d1c24a15cdd`.

## 1. Цель и правила работы

Подготовить игру к уровню с более чем 10 000 объектов, включая примерно 200 стульев, 100 столов, врагов и разрушения. Уменьшить постоянную стоимость кадра, пики при попаданиях и расход памяти при загрузке и входе в планировщик.

Этот файл — общий список работ и журнал результатов. Существующие механизмы перечислены отдельно: наличие кода не означает, что эффект подтверждён на компьютере игрока. Новые задачи пока не выполнены.

- `[ ]` — задача не завершена.
- `[x]` — результат проверен, ниже указано доказательство.
- Статусы в реестре: НЕ НАЧАТО / В РАБОТЕ / ПРОВЕРЕНО / БЛОКЕР / ОТЛОЖЕНО.
- После каждого этапа обновлять этот же файл: статус, коммит или PR, условия замера, результат и следующий шаг.
- Закрывать задачу после проверки поведения и замера. Если изменение не даёт пользы, записать результат эксперимента и откатить либо отложить его.
- Реализовывать по одному небольшому этапу. Перед изменением кода сверять актуальный main и инструкции репозитория.

## 2. Что известно сейчас

Аудит исходников выполнен; запуск и GPU-профилирование в этой среде не проводились. Ниже — признаки нагрузки, а не доказанный рейтинг времени кадра.

| Наблюдение | Значение и ограничение |
| --- | --- |
| Базовая карта | 1998 записей, 1446 прямых размещений GLB |
| Целые состояния прямых GLB | Оценка по именованным группам: 5216 поверхностей материалов, 1,59 млн треугольников по всей карте; архитектурные `.tscn` не включены |
| `08_office_desk_2` | 38 размещений × 13 мешей / 23 поверхности; 906 треугольников на целую модель |
| `06_simple_chair` | 122 размещения × 3 поверхности |
| `06_conference_chair` | 30 размещений × 6 мешей / 12 поверхностей |
| Голубая бутылка 500 мл | 53 размещения × 5 поверхностей |
| Свет | Глобальные динамические тени до 64 м; экраны допускают до 16 источников света и 4 источников теней |
| Статичная архитектура | Нет обнаруженного LightmapGI или архитектурных OccluderInstance3D |

Поверхности всей карты нельзя приравнивать к draw calls кадра: действуют видимость, отсечение и дополнительные проходы теней. Скрытые стадии разрушения нельзя считать видимой геометрией.

## 4. Этап 1 — сначала получить точные измерения

- [ ] **M01.** Зафиксировать оборудование, версию Godot, renderer, разрешение, настройки, коммит, карту и число объектов. Windows и Web измерять отдельно.
- [ ] **M02.** Подготовить повторяемые сценарии: спокойная комната; обзор загруженного участка; толпа; серия выстрелов; массовое разрушение; несколько облаков; запуск; перезапуск; вход и выход из планировщика.
- [ ] **M03.** После прогрева измерить одинаковый участок минимум три раза: время CPU/GPU, физику и скрипты, draw calls, видимые примитивы, активные тела, число узлов, RAM и доступные показатели VRAM. Недоступные показатели помечать явно.
- [ ] **M04.** Записать медиану и p95/p99 времени кадра, длительные кадры и пиковую память. Средний FPS не использовать как единственную метрику.
- [ ] **M05.** Сделать диагностические A/B-замеры с поочерёдным отключением теней, SSAO, мебели, контактных теней, дыма и активности врагов. После каждого теста возвращать исходные настройки.
- [ ] **M06.** Проверить зависимость от разрешения. Сильное улучшение при снижении разрешения указывает на вероятную нагрузку GPU по пикселям; вывод подтвердить профилировщиком.
- [ ] **M07.** Выбрать целевые бюджеты. Предложение для обсуждения: 60 FPS = 16,67 мс/кадр на основном ПК; отдельный бюджет для Web. Это цель, а не обещание результата.

**Готово, когда:** есть таблица baseline и подтверждённый рейтинг нагрузки отдельно для спокойной сцены, боя и загрузки.

## 5. Этап 2 — быстрые оптимизации

- [ ] **Q01.** A/B-проверить дальность глобальных теней 64/32/24 м и разрешение shadow map. Выбрать минимальные значения без заметных исчезновений теней.
- [ ] **Q02.** Проверить режим без теней экранов и с 1–2 источниками вместо 4. Сохранить свечение материалов и нужное освещение.
- [ ] **Q03.** Исключить из динамических теней малозаметные мелкие предметы; не отключать тени всего мира без визуальной проверки.
- [ ] **Q04.** Проверить стоимость SSAO и MSAA на фактическом renderer и версии движка. Подготовить уровни качества при значимом эффекте.
- [ ] **Q05.** Убрать повторный поиск лестниц каждые 0,35 с в неизменной игровой карте. Пересчитывать отверстия при загрузке и изменении лестниц в планировщике.
- [ ] **Q06.** Найти остальные регулярные обходы всех объектов. Заменять их локальными списками и событиями изменения только там, где профилирование подтвердило стоимость.
- [ ] **Q07.** Проверить CCD и contact monitoring: включать по необходимости, сохраняя защиту быстрых мелких тел от прохождения сквозь поверхности.

**Готово, когда:** эффект каждого принятого изменения измерен, свет, попадания и размещение не нарушены.

## 6. Этап 3 — целые модели и коллизии

- [ ] **A01.** Составить актуальный список стоимости каждой целой модели: число размещений, мешей, surfaces, материалов, треугольников и коллизий. Раздельно считать все стадии разрушения.
- [ ] **A02.** Начать с `08_office_desk_2`, `06_conference_chair`, бутылок и рулонов бумаги. Объединить совместимые части по материалу без изменения силуэта и стадии разрушения.
- [ ] **A03.** Проверить дубликаты одинаковых материалов. Совместно использовать неизменяемые ресурсы; настройки конкретного экземпляра хранить отдельно.
- [ ] **A04.** Применить атласы там, где они действительно сокращают surfaces. Не объединять непрозрачное стеклообразное покрытие, прозрачное стекло и разные режимы рендера в один неподходящий материал.
- [ ] **A05.** Подготовить простые коллизии заранее. Для шкафов сохранить отверстия, полки и опору для книг; для лестниц — проход и ступени; для дверей — проём.
- [ ] **A06.** Проверить общий кэш одинаковых shape-ресурсов. Не изменять форму одного экземпляра через общий ресурс.
- [ ] **A07.** Ограничить разрешение карт по фактическому экранному размеру предметов. Удалить ненужные normal/roughness-карты у гладкой кожи, стен и чёрного металла после сравнения вида.
- [ ] **A08.** Проверить mipmaps, VRAM compression и повторное использование текстур. Однотонная картинка того же размера сама по себе почти не экономит рендер.

**Готово, когда:** целая сцена содержит меньше surfaces и коллизий; разрушения, текстуры и планировщик проходят проверку.

## 7. Этап 4 — мебель до взаимодействия рисуется дёшево

Принцип: целые повторяющиеся предметы объединяются в MultiMesh по модели, материалам и небольшому сектору. Каждый предмет сохраняет стабильный ID, здоровье и простой способ получить попадание. Полноценный отдельный объект появляется при взаимодействии.

- [ ] **B01.** Сделать ограниченный прототип на одном типе стула. Сравнить обычные экземпляры и MultiMesh на 200, 1000 и 10 000 размещениях.
- [ ] **B02.** Выбрать размер секторов по замерам. Не собирать всю карту в один MultiMesh: отсечение должно оставаться локальным.
- [ ] **B03.** Добавить выход из пакета при толчке, импульсе, первом визуальном повреждении, отрыве от стены или редактировании в планировщике.
- [ ] **B04.** При подмене переносить transform, здоровье, object_id, seed/содержимое дисплея, следы попаданий и связи со столом/полкой. Удалять ровно один экземпляр из пакета.
- [ ] **B05.** Оставить дешёвый collision proxy для попаданий и взаимодействий. Не создавать заранее скрытый полноценный RigidBody для каждого предмета, если это сохраняет прежнюю стоимость.
- [ ] **B06.** Проверить одновременные попадания, повторную активацию, разрушение и загрузку сохранения: один предмет не должен дублироваться.
- [ ] **B07.** Расширять на столы, шкафы и мелочи по результатам прототипа. Прозрачные и уникальные предметы оценивать отдельно.
- [ ] **B08.** Оценить возврат неподвижного неповреждённого предмета в пакет после сна. Реализовывать только при измеримой пользе; повреждённые состояния сохранять корректно.

**Готово, когда:** draw calls и стоимость CPU снижаются, подмена незаметна, физика и сохранения сохраняют поведение.

## 8. Этап 5 — подготовленная архитектура и свет

Неподвижную 3D-геометрию всё равно нужно рисовать каждый кадр при движении камеры. Заранее готовим геометрию, свет, коллизии и данные видимости; это снижает стоимость кадра и запуска.

- [ ] **S01.** Классифицировать объекты по реальному поведению: неподвижные/неразрушаемые; подвижные; разрушаемые. Рамы и шахты лифтов отделить от движущихся дверей и кабины.
- [ ] **S02.** Объединить неподвижные непрозрачные меши по комнате или сектору и материалу. Сохранить локальное отсечение, проёмы и идентичность объектов для планировщика.
- [ ] **S03.** Подготовить статичные коллизии до запуска. Не превращать всю карту в одну чрезмерно сложную collision shape.
- [ ] **S04.** Сделать прототип LightmapGI на одной комнате: UV2, плотность lightmap, отсутствие швов и утечек света, размер памяти.
- [ ] **S05.** Запечь постоянное освещение архитектуры. Сравнить режимы запекания прямого/непрямого света; избежать двойного освещения от запечённых и оставшихся источников.
- [ ] **S06.** Сохранить динамический свет и тени для персонажей, подвижных дверей и нужных эффектов. Проверить переход между статичным и динамическим представлением.
- [ ] **S07.** Не запекать навсегда тени разрушаемой мебели на полу: после удаления предмета не должно оставаться его неподвижной тени. Для динамических предметов оценить probes и контактные тени.
- [ ] **S08.** Подготовить отдельный оптимизированный игровой уровень и исходную редактируемую карту; автоматически связывать их по версии/хэшу содержимого.
- [ ] **S09.** Для пользовательских карт в экспортированной игре предусмотреть доступную пакетную сборку геометрии и коллизий. LightmapGI нельзя запекать обычным способом в экспортированной игре.
- [ ] **S10.** Проверить готовые lightmaps в Windows и Web/Compatibility. Само запекание требует устройства с поддержкой RenderingDevice.

**Готово, когда:** уровень загружает готовую архитектуру, свет выглядит корректно, FPS и память измерены, редактор сохраняет возможность менять карту.

## 9. Этап 6 — не рисовать лишнее

- [ ] **V01.** Проверить frustum culling и границы пакетных объектов. Исправить слишком большие или неверные AABB.
- [ ] **V02.** Добавить простые архитектурные occluders у надёжных непрозрачных стен. Не закрывать ими окна, дверные проёмы и разрушаемые перегородки.
- [ ] **V03.** Проверить взаимодействие с режимом прозрачных стен/отверстия вокруг героя: он не должен скрывать нужные за стеной объекты через обычное occlusion culling.
- [ ] **V04.** Проверить LOD импортированных мешей и visibility ranges. Мелкие предметы упрощать или скрывать по экранному размеру с плавным переходом.
- [ ] **V05.** Для дальних помещений оценить HLOD — объединённое дешёвое представление комнаты. Менять на обычные объекты при приближении и взаимодействии.
- [ ] **V06.** Рассмотреть предзагрузку соседних секторов. Видимость, AI и коллизии управлять раздельно; скрытая комната не должна переставать удерживать физические тела.
- [ ] **V07.** Проверить, что туман сопровождается реальным ограничением дальнего рендера/LOD. Сам туман не исключает объекты из отрисовки.

**Готово, когда:** скрытые и далёкие части дешевле, без исчезновения нужных объектов и поломки проходов.

## 10. Этап 7 — разрушения, дым и следы

- [ ] **D01.** Расширить отдельные ресурсы стадий разрушения за пределы группы `03`. Целая модель не должна требовать загрузки всех мелких осколков.
- [ ] **D02.** Убрать синхронную тяжёлую загрузку стадии из момента попадания: ограниченная предзагрузка близких типов, кэш и бюджет подготовки. Сохранить немедленную реакцию на выстрел.
- [ ] **D03.** Ввести общий бюджет авторских физических фрагментов; существующий пул generic chunks не ограничивает их суммарное число.
- [ ] **D04.** Крупные значимые части оставить физическими; мелкую крошку сделать визуальной. Не дробить ножки мебели без необходимости.
- [ ] **D05.** Подготовить коллизии фрагментов заранее, отключать CCD и обработчики у неподвижных/затухающих частей, контролировать время жизни.
- [ ] **D06.** Ограничить число и перекрытие дымовых слоёв, добавить LOD и общий бюджет облаков. MultiMesh уменьшает вызовы отрисовки, но не стоимость прозрачных пикселей.
- [ ] **D07.** A/B-сравнить процедурный шум дыма с небольшой текстурой шума: отказ от PNG не гарантирует более дешёвый shader. Сохранить полупрозрачный зелёный дым.
- [ ] **D08.** Проверить стоимость маски стен у облаков: до 24 лучей с повторными попытками. Распределить подготовку по бюджету и использовать кэш без ошибок после разрушения стены.
- [ ] **D09.** Проверить бюджеты крови, отверстий, гильз, искр и воды: количество, срок жизни, материалы, геометрия и стоимость размещения следов.
- [ ] **D10.** Для следов повторно использовать геометрию и материалы; не создавать новый дорогой ресурс на каждое попадание без необходимости.

**Готово, когда:** серии разрушений и облаков не дают прежних длительных кадров, визуальный результат и попадания сохранены.

## 11. Этап 8 — враги и физика

- [ ] **E01.** Проверить эффективность существующих AI/animation LOD и общего бюджета поиска пути на возрастающем числе врагов.
- [ ] **E02.** Измерить отдельно движение, поиск пути, проверку препятствий, скелетную/процедурную анимацию, хитбоксы, кровь и звук.
- [ ] **E03.** Для дальних врагов снижать частоту тяжёлых проверок, распределяя работу по кадрам. Сохранить реакцию на бой и прохождение препятствий.
- [ ] **E04.** Проверить лишнюю работу до раннего выхода для далёких и мёртвых врагов. Отключать завершившиеся эффекты и обработчики по событиям.
- [ ] **E05.** Ограничить одновременно активные ragdoll/части тела, переводить успокоившиеся трупы в дешёвое представление с нужной коллизией.
- [ ] **E06.** Проверить collision layers/masks, число контактов, перекрытия мебели и тел. Неподвижные объекты не должны постоянно будить соседей.

## 13. Дополнительные варианты — выбирать по результатам

| Вариант | Когда полезен | Ограничение / решение |
| --- | --- | --- |
| Упрощённый shader пола | GPU тратит много времени на большой экранный участок пола | Сравнить текущие выборки шума и clearcoat с более простым материалом |
| Пакетные контактные тени | Много отдельных прозрачных quad под мебелью | A/B-проверить общий рендер и дистанционное отключение; не дублировать запечённые тени |
| Forward+ или Mobile вместо Compatibility | Замеры показывают преимущество на целевом ПК | Не считать смену renderer гарантированной оптимизацией; Web проверяется отдельно |
| Масштаб рендера / уровни качества | Упор в GPU, разные устройства | Пользовательские настройки качества; проверить читаемость интерфейса |
| Impostors для далёкого города | Силуэты фона остаются дорогими | Проверить текущий MultiMesh города до усложнения |
| Аудиобюджет | Много голосов, столкновений и эффектов | Приоритет ближайших/значимых звуков, без задержки ключевых сигналов |
| Работа напрямую через RenderingServer/PhysicsServer | После batching остаётся доказанная стоимость тысяч узлов | Более сложная архитектура; применять только к ограниченному проблемному участку |
| Потоки для чистых расчётов | Подготовка данных блокирует CPU | Не переносить небезопасные операции SceneTree в фон; проверить синхронизацию |
| Фиксированные фоновые изображения | Действительно неизменный вид камеры | Для свободной камеры и интерьерных стен обычно не подходит |

- [ ] **X01.** Проверить shader пола и контактные тени.
- [ ] **X02.** Сравнить renderers и уровни качества на целевых устройствах.
- [ ] **X03.** Проверить аудио и фон города.
- [ ] **X04.** Решить, нужны ли Server API и фоновые расчёты после основных изменений.

# O04 — цена CPU-запекания крови

Инкремент T004: выполнена исходная задача аудита **измерить** одинаковые серии
попаданий. Production-код не менялся; ускорение и прирост FPS не заявляются.
Владелец масок, геометрии и leases остаётся features.infected. Добавлены только
локальный fixture/entrypoint в его tests, stdlib runner в tools и доказательства.
Public API, сцены, ассеты, RG8/128×128, DTO, зависимости и policy прежние;
архитектурных исключений нет. Два новых GDScript не более170 строк, функции ниже50.

## Протокол

Godot4.7.2, Linux x86_64, виртуальный AMD EPYC9V74,9 видимых CPU. База production:
`a19bdf68c3bbc485fb1ad7811386785d603bb2af`. Поле revision в JSON обозначает эту
базу; инструменты измерения тогда были незакоммиченными файлами данного PR.
Один процесс Godot за раз; каждый случай с пустым XDG_DATA_HOME. Это измерения
общей виртуальной машины: время зависит от нагрузки хоста, абсолютные числа не
переносятся на компьютер игрока.

Настоящие авторские сцены,90 тел:54 Hunger,18 Revenant,6 Brute,6 Titan,
3 Colossus,3 Horde. AI, анимация и физика отключены через родителя fixture.
Настоящие BodyParts, геометрия, masks/material pages/leases сохраняются. Настройка
сцены отдельно от попаданий. Первое попадание в каждое тело отдельно учитывает
ленивые Image и Texture2DArray, включая первую загрузку страницы данного типа.
Далее3 прогревочных process_frame и60 idle кадров перед серией.

Это **подтверждённые раны**, не выстрелы через игровой Weapon/Projectile:
нет raycast, промахов, HP, скорострельности с квантизацией physics tick, смерти,
пробития или отрыва частей. Номинальный шаг1/60с; частота и число дробин читаются
runner из текущих shotgun/minigun сцен (default pellets1 соответствует Rifle).
SHOTGUN1,1/с ×8, MINIGUN24/с ×1. В600 шагах:11 очередей/88 ран и240/240.
В native180 шагах:4/32 и72/72. При замедлении реального процесса сценарий не
пропускает попадания и не пытается выдерживать wall-clock частоту выстрелов.

Порядок actor/triangle задаётся формулой в fixture: центр настоящего треугольника,
радиус из BodyParts.wound_radius с поправкой world_scale; дробины распределены
между3 телами. Это одинаковая детерминированная нагрузка, а не распределение
реальных столкновений в миссии. Холодная серия охватывает все шесть типов. Warm minigun600:144/48/16/16/8/8
попаданий по типам в указанном порядке, shotgun600:54/23/3/5/0/3.
В коротком native shotgun только19 Hunger/13 Revenant; native minigun охватывает
все шесть. Это ограничение распределения, не равная частота попаданий по типам.

Для каждого оружия три пути в отдельных процессах:

- full — настоящий BodyParts.add_rest_wound без внутренних счётчиков;
- stages — та же последовательность create_masks/paint/update_layer, отдельно
  измерены CPU интервалы и числа загрузок;
- scan — только обход всех треугольников и настоящий BAKE._near, без рисования.

Full/stages обязаны иметь одинаковую топологию и **SHA256 всех исходных RG8 байтов
масок**, число масок и размеры. Это проверка эквивалентности инструментации;
нового production алгоритма для сравнения здесь нет. Время scan — отдельный
микрозамер с дополнительным счётчиком, не точное разложение full вычитанием.
После серии12 повторов уже нарисованной первой раны и12 заведомо внешних ран.
Runner проверяет0 изменённых uploads в этих controls у stages, количество событий,
отсутствие SCRIPT ERROR/ERROR и утечек; тайминги не являются flaky assertions.

## Повторение

```bash
python tools/profile_body_blood.py --godot /path/to/godot \
  --output /tmp/body_blood.json --log-dir /tmp/body_blood_logs
# Быстрая проверка протокола: --smoke (3 Hunger,30 шагов,1 повтор).
# PNG исходных масок первого/последнего тела: --captures /tmp/blood_captures
```

Для OpenGL запустить доступный X display, затем ту же команду с
`--native --frames=180 --repeat=1 --captures /tmp/blood_native`.
Здесь использовался Xvfb640×360 через TCP DISPLAY=127.0.0.1:123,
LP_NUM_THREADS=4. Native mode означает настоящий renderer вместо headless;
программный Mesa/llvmpipe не является аппаратной видеокартой игрока.

## Границы результата и дальнейшее решение

`active_batch` включает только применение ран. Сравнение с16,667мс показывает,
может ли эта работа сама занять бюджет60Hz, но не её процент в игровом кадре.
Observed process_frame intervals включают ожидание/рендеринг стенда, не FPS миссии.
`update_layer_cpu_usec` — время CPU вызова/постановки загрузки, **не GPU execution**.
Видео monitor и nominal page payload не дают полного VRAM: payload учитывает только
RG8 массивы по128 слоёв, без других ресурсов/выравнивания/драйвера.

Приоритет следующего отдельного эксперимента — неизменяемый пространственный
индекс кандидатов треугольников. Сначала доказать byte-for-byte mask parity для
краёв/швов/разных радиусов и серий; сохранить порядок записи и размер/вид крови.
Память индекса учитывать в бюджете и eviction body_mesh_cache, а не создавать
неограниченный static cache. Объединение uploads пока не имеет доказанного
выигрыша на аппаратном GPU: требуется профиль и сохранение frozen snapshots
piece_skin, lease lifetime/reuse и финальной маски при смерти/отрыве.
Windows, WebGL2 fallback и аппаратный Forward+ не профилировались. Этим стендом
не объясняется зависание первых секунд полной миссии. Следующая задача исходного
аудита с конкретным исполнимым результатом — Q01, полнота запуска suites в CI.
